# Gotcha 萃取指引

`skill-summary` 主檔保留四個維度的綱要，本檔提供每個維度的判讀細節、範例、邊界處理。

---

## 維度 1 — 目標 skill 識別細節

### 使用者沒指定 skill 名稱時的處理

| 訊號 | 處置 |
|---|---|
| 「剛才那個 skill」 | 從對話前文找最近觸發的 skill |
| 「review skill 沒抓到」 | 推斷是 `skill-review`（用 hard trigger 反推） |
| 完全沒提 skill 名 | 直接問：「你剛才使用的是哪個 skill？或踩坑的是哪個？」 |

### inspect-gotchas.sh 輸出的判讀

| STATUS | 含義 | 處置 |
|---|---|---|
| `ok` | 3–6 條，可正常加 | 走標準流程 |
| `under-min` | < 3 條 | 可正常加，但提示「skill 本身 Gotchas 偏少，可能是新 skill」 |
| `over-limit` | > 6 條 | **觸發 G3**——建議 skill-review 評估重構，不直接加 |
| `no-gotchas-section` | 沒有 ## Gotchas 段 | 草稿改成「整段 Gotchas」格式（含 H2 標題） |

## 維度 2 — 錯誤事實萃取細節

### 「具體可驗證的事實」判準

事實必須包含三要素：

1. **誰**：使用者輸入了什麼？
2. **做了什麼**：skill 做了什麼動作（或沒做什麼）？
3. **預期 vs 實際**：應該怎樣 vs 實際怎樣？

### 萃取範例

#### ❌ 拒絕模糊敘述

> 使用者：「skill-brain 卡卡的」

→ 追問：
- 卡在哪一步？
- skill 做了什麼？
- 你預期要什麼？

#### ✅ 接受具體敘述

> 使用者：「我跟 skill-brain 說『要做一個訂單系統的 skill』，結果它在維度 1 還是逐一問我『重複性』『baseline』『第一場景』，但這三個問題我在第一句話就講過了——它沒判讀就機械式問。」

→ 三要素齊全：
- 誰：使用者貼出明確的訂單 skill 構想
- 做了什麼：skill-brain 沒判讀既有訊息，機械式問三個問題
- 預期 vs 實際：應該按 SKILL.md 講的「能判讀的就判讀」

### 症狀寫法

把萃取出的具體事實，壓成 1–2 行：

> **症狀**：使用者在第一句話已給齊維度 1 的三個答案，skill-brain 仍機械式逐一提問。

關鍵：保留「使用者狀態 + skill 行為 + 落差」三要素。

## 維度 3 — 正確做法判讀細節

### 三種來源的優先順序

1. **使用者直接告知**（最高優先）：使用者明確說「應該先 X 再 Y」
2. **skill 自己的設計原則**：SKILL.md 中已寫但 Claude 沒遵守的原則
3. **鄰居 skill 的處理方式**：類似情境其他 skill 怎麼做

### 判讀範例（接續維度 2 的範例）

回到 skill-brain 機械式提問的案例：

- 使用者沒明確告知 → 從 SKILL.md 找
- skill-brain 主檔寫：「不必按順序機械式提問——能直接判讀的就判讀，缺什麼補什麼」
- → 正確做法：「先掃使用者既有訊息判讀已給的維度，只問真正缺的部分」

### 寫法

| ❌ 空話 | ✅ 可執行 |
|---|---|
| 「請小心判讀」 | 「先掃使用者既有訊息判讀已給的維度，只問真正缺的」 |
| 「注意彈性」 | 「能從 5 句話判讀的維度直接寫入摘要，不再追問」 |
| 「使用時要細心」 | 「進入維度 1 前先 echo 已判讀的內容給使用者確認」 |

## 維度 4 — 為什麼有見解細節

### 「設計層面的洞察」三類

1. **違反了哪條原則**：「違反 SKILL.md 維度 1 的『能判讀就判讀』原則」
2. **為什麼錯誤容易發生**：「機械式跑 Step 1→2→3 的慣性比『判讀後跳步』更省認知」
3. **為什麼正確做法是對的**：「dogfooding 證實使用者通常在第一句話就給齊基本資訊」

### 寫法範例

繼續上面的例子：

> **為什麼**：違反 skill-brain 自己訂的「能判讀就判讀」原則。Claude 容易掉進「機械式跑流程」的慣性,因為按順序問比掃描判讀更省認知;但這違反 skill 設計初衷,且讓使用者重複講已說過的話,體驗變差。

關鍵：給 Claude **下次能舉一反三**的洞察，不只是記住單一情境。

### 使用者敘述

> 「我跟 skill-brain 說『要做一個訂單系統的 skill』,結果它在維度 1 還是逐一問我『重複性』『baseline』『第一場景』,但這三個問題我在第一句話就講過了。」

### 萃取結果

```
### G6：機械式跑維度提問,沒判讀使用者既有訊息

**症狀**：使用者在第一句話已給齊維度 1 的三個答案,skill-brain 仍逐一機械式提問。

**正確做法**：進入維度 1 前先掃使用者既有訊息,echo 已判讀的內容(「我看到你已經提到 X、Y、Z」),只問真正缺的部分。

**為什麼**：違反 skill-brain 自己訂的「能判讀就判讀」原則。Claude 容易掉進「機械式跑流程」的慣性——按順序問比掃描判讀更省認知,但這違反 skill 設計初衷,且讓使用者重複講已說過的話,體驗變差。
```

## 跨 skill 路由錯的雙向處理

當錯誤類型是 D（Step 0 表）——「該用 X 結果觸發到 Y」——必須**產出兩份草稿**：

### 給誤觸發的 skill Y 加 anti-trigger Gotcha

```
### GN：誤觸發 X 的情境（應走 X）
**症狀**：使用者描述 <情境>，本應走 <X>，但被本 skill 攔截。
**正確做法**：在 description 的 DO NOT trigger 加上「<情境關鍵詞>（用 X）」；對話中發現也立刻退出。
**為什麼**：<X> 才是該情境的正確處置者，本 skill 越界處理會給出錯誤輸出。
```

### 給該觸發的 skill X 加觸發詞 Gotcha

```
### GN：<情境> 觸發詞太弱被 Y 搶走
**症狀**：使用者描述 <情境>，期望觸發本 skill，但被 <Y> 搶走。
**正確做法**：在 description 觸發關鍵字加上「<關鍵詞>」「<關鍵詞>」等更明確的詞。
**為什麼**：原本的觸發詞太抽象（如「處理」「協助」）容易被通用詞庫覆蓋。
```

兩份草稿都要附上各自的 inspect-gotchas.sh 結果（NEXT_ID、LAST_LINE 各自不同）。
