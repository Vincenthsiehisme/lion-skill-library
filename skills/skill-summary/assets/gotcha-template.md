# Gotcha 草稿範本

這份範本是 `skill-summary` 產出 Gotcha 草稿時的標準格式。對應skill 的三段式結構。

---

## 標準格式

    ### G<N>：<症狀的一句話標題>
    **症狀**：<具體事實，含使用者狀態 + skill 行為 + 落差三要素>
    **正確做法**：<一句話、動詞開頭、可執行>
    **為什麼**：<設計層面的洞察——違反原則、為何容易發生、為何正確做法對>

---

## 完整範例

    ### G6：機械式跑維度提問,沒判讀使用者既有訊息

    **症狀**：使用者在第一句話已給齊維度 1 的三個答案,skill-brain 仍逐一機械式提問。

    **正確做法**：進入維度 1 前先掃使用者既有訊息,echo 已判讀的內容(「我看到你已經提到 X、Y、Z」),只問真正缺的部分。

    **為什麼**：違反 skill-brain 自己訂的「能判讀就判讀」原則。Claude 容易掉進「機械式跑流程」的慣性——按順序問比掃描判讀更省認知,但這違反 skill 設計初衷,且讓使用者重複講已說過的話,體驗變差。

---

## 變體 1：no-gotchas-section（目標 skill 沒有 ## Gotchas 段）

如果 inspect-gotchas.sh 回傳 STATUS=no-gotchas-section，草稿要含整個 H2 區塊：

    ---

    ## Gotchas

    ### G1：<標題>
    **症狀**：...
    **正確做法**：...
    **為什麼**：...

並在插入指引中註明：「插入到 SKILL.md 結尾（## Reference Files 之前如有此段）」。

---

## 變體 2：跨 skill 路由錯（雙向處理）

當錯誤類型是「該用 X 結果觸發到 Y」，產出兩份草稿：

### 草稿 A — 給誤觸發的 Y 加 anti-trigger Gotcha

    ### GN：誤觸發 <X 情境>（應走 X）
    **症狀**：使用者描述 <情境>，本應走 <X>，但被本 skill 攔截。
    **正確做法**：在 description 的 DO NOT trigger 加上「<情境關鍵詞>（用 X）」；對話中發現也立刻退出。
    **為什麼**：<X> 才是該情境的正確處置者，本 skill 越界處理會給出錯誤輸出。

### 草稿 B — 給該觸發的 X 加觸發詞 Gotcha

    ### GN：<情境> 觸發詞太弱被 Y 搶走
    **症狀**：使用者描述 <情境>，期望觸發本 skill，但被 <Y> 搶走。
    **正確做法**：在 description 觸發關鍵字加上「<具體關鍵詞>」等更明確的詞。
    **為什麼**：原本的觸發詞太抽象容易被通用詞庫覆蓋。

兩份草稿要附上各自的 inspect-gotchas.sh 結果（NEXT_ID、LAST_LINE 各自不同）。
