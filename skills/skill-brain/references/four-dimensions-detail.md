# 四維度釐清細節

`skill-brain` 主檔保留四個維度的綱要，本檔提供每個維度的判斷紅燈、操作細節、範例。

---

## 維度 1 — Problem Statement

### 三個必須釐清的子維度

| 子維度 | 為什麼重要 | 從訊息能直接判讀的線索 |
|---|---|---|
| **重複性** | skill 的本質是重複任務的封裝；低於月 3 次的任務做 skill 不划算 | 「每週都要…」「每次客戶問…」「上次也是這樣…」 |
| **Baseline** | 找出沒有 skill 時的成本，對比 skill 的增量 | 「現在我都用一段 prompt…」「我有寫 SOP 但…」 |
| **第一個觸發場景** | 強迫具體化，避免抽象的「以後可能用得到」 | 「下週要做 X 任務」「明天會議要…」 |

### 紅燈訊號

| 訊號 | 處置 |
|---|---|
| 「以後可能用得到」「先做起來放著」 | 沒有真實場景，建議**暫緩**——把 intent 標記 `parked` |
| 「每次想到的時候不太一樣」 | 問題還沒收斂，建議**先用 prompt 處理 5 次**找出共同模式再回來 |
| 「這個應該很簡單」 | 通常代表還沒踩過坑，建議**先實際做幾次手動版**再評估 |
| 「這個一次性的就好」 | 直接告訴使用者：低頻任務直接用 prompt 比做 skill 划算 |

### 對話範例

✅ **可往下走的描述**：
> 「我每週要審 3–5 個 PR 的 commit message，每次都要重複貼一段檢核清單，想做個 skill 自動化」

→ 重複性（每週 3–5 次）✅、baseline（手動貼清單）✅、第一場景（下次 PR）✅

❌ **要回頭問的描述**：
> 「我覺得我的工作流好像可以做成 skill，要不要試試？」

→ 三個子維度全空，回頭問：「你最近一次想到這件事，是因為哪個具體任務？」

## 維度 2 — Trigger 邊界

### 三類觸發詞的數量規範

| 類別 | 最少 | 最多 | 想不出來的訊號 |
|---|---|---|---|
| Hard | 3 | 5 | 核心動詞不夠明確，回維度 1 重新釐清 problem |
| Soft | 2 | 5 | skill 沒有情境性使用——大多數 skill 都該有，極少例外 |
| Anti | 2 | 不限 | 邊界沒想清楚，下一維度重疊掃描會撞牆 |

### Hard trigger 的品質判準

❌ **太抽象**：「skill」「工具」「幫忙」「處理」 → 通用詞會被所有 skill 搶觸發，等於沒設

✅ **夠具體**：必須是該 skill **獨有的動詞 + 名詞組合**
- 「審 skill」對 `skill-review`（審 + skill）
- 「補資料字典」對 `data-dictionary-advisor`（補 + 資料字典）
- 「查 ERP table」對 `erp-schema`（查 + ERP table）

### Anti-trigger 的寫法

對每個容易混淆的鄰居 skill，列出「會被誤觸發但其實該走鄰居 skill」的詞：

```
DO NOT trigger for:
- 已經有 skill 草稿要審查（用 skill-review）
- 要動筆寫 SKILL.md（用 skill-create）
```

格式：`<情境描述>（用 <鄰居 skill 名>）`

## 維度 3 — Boundary

### 「做」這一句的三個約束

1. **動詞開頭**：寫「在動筆前釐清 skill 意圖」，不寫「skill 意圖的釐清工作」
2. **一句話**：超過一句代表 skill 範圍太雜
3. **具體**：寫「掃描既有 skill 找重疊」，不寫「分析相關情況」

### 「不做」清單的三個約束

1. **點名具體鄰居**：寫「不寫 SKILL.md（用 skill-create）」，不寫「不做撰寫類工作」
2. **2–3 條**：少於 2 條代表邊界沒想清楚；多於 3 條代表 skill 範圍太雜
3. **動詞開頭**：寫「不評分既有 skill」，不寫「skill 評分」

### 範例對照

❌ **模糊版**：
```
做：幫助使用者規劃 skill
不做：不做其他無關的事
```

✅ **具體版**：
```
做：在動筆寫 SKILL.md 前，把問題、觸發詞、邊界釐清。
不做：
- 不寫 SKILL.md（用 skill-create）
- 不審查既有 skill（用 skill-review）
- 不做產品 PRD（用 prd-writer，那是給產品功能用的）
```

## 維度 4 — 重疊掃描操作

### 執行步驟

1. **列出 skill 庫**：`ls /mnt/skills/user/`
2. **逐一讀 frontmatter**：每個 SKILL.md 只讀前 30 行（含 YAML frontmatter）
3. **三層比對**：
   - **動詞重疊**：兩個 skill 的核心動詞相同（都「審查」「設計」「查詢」）
   - **名詞重疊**：兩個 skill 處理同一名詞（都處理「schema」「skill」「PRD」）
   - **Trigger 詞字面重疊**：description 中的觸發詞有交集
4. **列成表格**交給使用者，由使用者填處置欄

### 嚴重度判準

| 嚴重度 | 判準 | 建議處置（給使用者參考） |
|---|---|---|
| 🔴 高 | 核心職責 70%+ 重疊 | 強烈建議改做既有 skill 的擴充，不另立新 skill |
| 🟡 中 | trigger 詞會搶觸發、職責部分重疊 | 必須調整 trigger 或加 anti-trigger |
| 🟢 低 | 邊界相鄰但職責不同 | 在「不做」清單點名鄰居 skill 即可 |

### 重要原則

**只列出，不主動判定**——本 skill 只負責呈現重疊事實，使用者比 brain 更了解業務脈絡，處置權在使用者。

### 性能優化（給未來 50+ skill 時參考）

當 skill 庫超過 50 個時，frontmatter 全讀會慢。優化策略：
1. 先用使用者描述中的 hard trigger 詞，`grep` 過濾 user 目錄找出可能撞詞的 skill
2. 只對 grep 命中的 skill 讀 frontmatter
3. 仍要做一次「全庫快速掃」找名詞重疊（不只是字面 trigger 重疊）

目前 27 個 skill 全讀仍在合理範圍，暫不需要優化。
