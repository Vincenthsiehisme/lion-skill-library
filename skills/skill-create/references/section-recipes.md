# Skill 段落寫法食譜

每個段落的標準格式、寫作判準、反例。配合 `skill-anatomy.md` 的骨架選型使用。

---

## Description 段

### 標準三段式（v2 規格）

```yaml
description: |
  <定位句，≤ 40 字。寫「X 做什麼，給誰用」>。

  Trigger: <鑽石詞 1>、<鑽石詞 2>、<鑽石詞 3>、<鑽石詞 4>；或<1 條兜底情境句，≤ 50 字>。

  Do NOT: <場景 1> → <neighbor-skill-1>；<場景 2> → <neighbor-skill-2>。
```

**frontmatter 必須加 `schema_version: v2`**，否則 validate 腳本會走 v1 legacy 規則。

### 定位句寫法

✅ **好的**：
- 「Skill 規劃階段的釐清顧問」
- 「雄獅 ERP 資料庫 schema 查詢顧問」
- 「把已拍板、1 sprint 內小功能寫成薄 PRD」

❌ **差的**：
- 「可以幫忙處理 skill 相關問題」（不夠 pushy）
- 「一個關於 skill 的工具」（沒講做什麼）
- 「處理使用者的 skill 需求」（範圍太廣）

**長度**：≤ 40 字。不要把 trigger 訊號塞進定位句。

### Trigger 段寫法（鑽石詞 + 情境句）

**結構**：`Trigger: <鑽石詞>、<鑽石詞>、...；或<情境句>。`

**鑽石詞**：
- 數量 **3–6 個**（少於 3 容易 undertrigger，多於 6 回到流水帳）
- 用**頓號**分隔（不要用引號包裹——引號會讓字面匹配變嚴格）
- 該領域的「術語 / 工具名 / 動詞片語」，使用者一講就該觸發
  - ✅ 「寫 sprint PRD」「萃取我的 fingerprint」「跑進化診斷」
  - ❌ 「使用工具」「幫我」「查一下」（太泛）

**情境句**（兜底召回）：
- 1 條，≤ 50 字
- 抓「沒講關鍵字但意圖明確」的情境，通常用第一人稱
  - ✅ 「使用者已有 FR / Anchor 草稿要組規格」
  - ✅ 「使用者貼 error log 並暗示是線上現象」
  - ❌ 「使用者需要幫助時」（沒意圖訊號）

### Do NOT 段寫法（最易誤觸鄰居）

✅ **好的**：點名 **2–3 個最易誤觸**的鄰居
```
Do NOT: 問題仍在探索期 → prd-writer；轉 API 規格 → story-orchestrator；派工 → task-dispatcher。
```

❌ **差的**：列所有鄰居當噪音
```
Do NOT: 探索期 → prd-writer；轉 API 規格 → story-orchestrator；派工 → task-dispatcher；
        審查 → skill-review；寫報告 → strategy-case-report；批判 → critical-reviewer。
```

❌ **更差**：寫空話
```
Do NOT: 其他無關需求、與本 skill 無關的問題
```

**怎麼選最易誤觸鄰居**：想像 Claude 路由時會卡在哪 2–3 個語感相近的 skill。其他鄰居不會進候選池，列了也沒用。

### Description 長度

**全段 ≤ 250 字**（含換行，validate 會自動檢查）。

實務上的字數分配：
- 定位句 ≤ 40 字
- Trigger 段 ≈ 80–120 字（鑽石詞 + 情境句）
- Do NOT 段 ≈ 60–90 字（2–3 條）

超過 250 字就是流水帳警告，validate 會抓。

## Description 段（v1 legacy 規格 — 既有 skill 用）

**僅當 skill 沒寫 `schema_version: v2` 時適用**。漸進派路線：既有 skill 不需要強制升級。

v1 四段式：

```yaml
description: |
  <定位句>。當<觸發情境>時觸發。<簡述做什麼>。

  觸發關鍵字：<詞 1>、<詞 2>、...（8–12 個）。

  [可選] 也在以下情境觸發：<隱性觸發>。

  DO NOT trigger for: <情境>（用 <skill-1>）、<情境>（用 <skill-2>）...
```

v1 → v2 升級時用 `validate-skill.sh --strict <skill-dir>` 找出該改的位置。

## Step 0 段（問診式）

### 標準格式

範例：

    ## Step 0：判斷使用者在哪個階段

    每次對話開始，**先快速判讀使用者的清楚程度**，不必直接問（多數時候從訊息就看得出來），只在判讀不出時問一次：

    > 「<選擇題>
    > A）<選項 1>
    > B）<選項 2>
    > C）<選項 3>」

    | 回答 | 進入路徑 |
    |---|---|
    | A | → <路徑說明> |
    | B | → <路徑說明> |
    | C | → <路徑說明> |

    **例外**：<什麼情況跳過問診>。

### 寫作要點

- **三選一為佳**——少於 3 個分流不夠細，多於 4 個讓使用者選不下手
- **路徑差異化**——A/B/C 對應的後續流程要明顯不同，否則就不該分流
- **預設可判讀**——強調「不必直接問」，避免每次都丟問題給使用者
- **例外情境必寫**——什麼時候跳過 Step 0，避免機械式執行

## 核心流程段（維度式 vs 步驟式）

### 維度式（推薦，顧問類 / 產出類用）

範例（注意縮排，這是檔案內容範例）：

    ## 核心流程：N 個維度的釐清

    skill 的工作是確認以下 N 個維度都已釐清。**不必按順序機械式提問**——能直接判讀的就判讀，缺什麼補什麼。

    ### 維度 1 — <名稱>
    [內容]

    ### 維度 2 — <名稱>
    [內容]
    ...

**特徵**：
- 維度間**允許跳躍**（順序可調）
- 每個維度有獨立判準
- 強調「能判讀就判讀」的彈性

### 階段式（流程類用）

範例：

    ## Phase 1: <階段名>
    ### Step 1.1: <子步驟>
    ### Step 1.2: <子步驟>

    ## Phase 2: <階段名>
    ### Step 2.1: ...

**特徵**：
- Phase 間**不能跳**（強制順序）
- 每個 Phase 有里程碑產出
- 用於有時序依賴的工作流

### 反例：步驟式（避免）

❌ **避免這樣寫**：

    ## 流程

    ### Step 1: ...
    ### Step 2: ...
    ### Step 3: ...
    ### Step 4: ...
    ### Step 5: ...
    ### Step 6: ...

**問題**：
- 沒有階段感，使用者無法判斷「我現在做完一半了沒」
- 機械式線性，違反 dim 4 railroading 原則
- 步驟太多容易踩錯順序

## Gotchas 段（強制三段式（對應 Anthropic dim-2 規範））

### 標準格式

範例：

    ## Gotchas

    ### G1：<症狀的一句話標題>
    **症狀**：<具體描述使用者遇到的問題或錯誤行為>
    **正確做法**：<該怎麼做才對>
    **為什麼**：<背後原因或設計考量>

    ### G2：...

### 寫作判準

| 維度 | 標準 | 反例 |
|---|---|---|
| **數量** | 3–5 條為佳 | 1–2 條太少；6+ 條代表沒收斂 |
| **症狀具體性** | 「使用者貼出工單描述問是不是 skill 邊界」 | ❌「使用時要小心邊界問題」 |
| **正確做法可執行** | 「先問『這個任務一個月會做幾次？』」 | ❌「請謹慎判斷」 |
| **為什麼有見解** | 「skill 的成本是寫+維護+觸發判讀，低頻任務直接用 prompt 划算」 | ❌「因為這樣不好」 |

### Gotchas 來源

每條 Gotcha 應該來自：
1. **使用 reference-bundle 萃取出的常見錯誤**（從其他 skill 借鏡）
2. **預判使用者會踩的坑**（從 skill 的設計盲點推出）
3. **後續使用累積**（由 `skill-summary` 寫回）

純粹的「應該注意」「請小心」是空 Gotcha，會被 review 打回。

## 與其他 skill 的銜接段

### 標準格式（雙段式）

範例：

    ## 與其他 skill 的銜接

    <skill 名> 的職責是 <核心定位>。<說明邊界>。

    ### 正向銜接（被誰呼叫 / 完成後給誰）

    | 上下游 | 動作 |
    |---|---|
    | 上游：<skill 名> | <傳入什麼> |
    | 下游：<skill 名> | <交給誰做什麼> |

    ### <skill 名> 內部不處理的事

    下列情境不該進到 <skill 名> 主流程，已在 description 的 Do NOT 段中排除：

    - <情境 1> → 應走 <鄰居 skill>
    - <情境 2> → 應走 <鄰居 skill>
    - ...

    如果在對話中**才發現**使用者要的不是這個 skill，做法是：直接告知並導向對應 skill，**結束對話**。不要在內部接手非範疇的需求。

### 寫作要點

- **必有「正向銜接」+「內部不處理」雙段**——只寫正向銜接會缺擋牆
- **不主動路由**——「內部不處理」時只告知並結束，不接手非範疇需求
- **與 description 的 Do NOT 段對齊**——兩處不能矛盾（v1 legacy skill 則是與 DO NOT trigger for 對齊）

## 輸出規格段（產出類專屬）

### 標準格式（雙交付物）

範例：

    ## 輸出規格（雙交付物）

    ### 交付物 A：<主要產出>
    [完整檔案 / 目錄結構，給使用者部署用]

    ### 交付物 B：對話摘要
    [在對話中渲染，給使用者人眼快速確認]

    （以下為對話摘要的渲染範例）
    ━━━━━━━━━━━━━━━━━━━━━━━
    <emoji> <Skill 名> 摘要

    【關鍵欄位 1】xxx
    【關鍵欄位 2】xxx
    ...
    【建議下一步】交給 <下游 skill>
    ━━━━━━━━━━━━━━━━━━━━━━━

    **兩者都要產出**——完整產出給使用者部署、對話摘要給人眼確認。

### 寫作要點

- **雙交付物是通用慣例**，產出類 skill 必須遵守
- 對話摘要用裝飾線（━）框起來，emoji 開頭，便於使用者快速辨識
- 摘要結尾必有「建議下一步」欄位，明確指向下游 skill
