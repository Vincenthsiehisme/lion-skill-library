# 狀態快照（Status Snapshot）

**僅在 Guided Mode 啟用**。Draft Mode 不出狀態快照，缺口統一進入 Unknown Register。

Guided Mode 下，每次輸出章節內容後，**停下來**，輸出評估快照並等待 PM 回應。
不自動繼續到下一個問診或下一個章節。

---

## 前置步驟：讀取 Anchor

若對話中存在 Anchor Statement：
- 直接從 Anchor 的「PRD 章節狀態」欄位讀取各章節狀態，不需重新掃描對話
- 快照輸出後，若 Anchor 章節狀態與快照不一致，以快照為準並更新 Anchor

---

## 格式

```
─────────────────────────────
[章節名稱] 完成

完整度：
[達標]：[具體達標的項目]
[缺口]：[缺口描述]（[為什麼現在值得處理的理由，一句話]）
[未填]：[項目名稱]

→ A) 現在補  B) 標記待補，繼續下一章節  C) 直接繼續，不補
─────────────────────────────
```

**回應方式：** PM 回 A / B / C 即可。

- **A**：針對缺口繼續問診，補完後重新輸出該章節，再次顯示快照
- **B**：把缺口加入開放問題清單與 Unknown Register，標記 `[待確認]`，繼續下一章節
- **C**：直接進下一章節，不問、不標記、不提醒

---

## 建議理由的判斷邏輯

快照裡的「為什麼現在值得處理」只在滿足以下至少一條時才寫，否則不給建議：

1. **PM 可能不知道這個缺口**：這是新資訊，不是 PM 主動跳過的
2. **這個缺口影響下一步能不能做**：例如「Why now 不清楚，Metrics 的 OKR 連結會無法填」
3. **現在補成本最低**：例如「背景資訊現在腦子裡有，之後要重新回憶」

不滿足任何一條，只列事實（[達標] / [缺口] / [未填]），不給建議理由，不催促。

## 狀態標籤定義

| 標籤 | 意思 |
|------|------|
| [達標] | 達到品質門檻 |
| [缺口] | 有內容但未達門檻（空洞或缺要素） |
| [未填] | 空白或缺失 |
| [本次未涉及] | 本次未涉及，不評分 |

---

## 品質門檻對照（判斷 [達標] / [缺口] / [未填] 的依據）

| 章節 | [達標] | [缺口] | [未填] |
|------|---------|------------|-----|
| 背景 | 誰受影響 + 規模 + Why now | 缺任一項 | 空白 |
| 目標 | L1 假設聲明完整（主指標 + 行為假設 + 商業結果 + 失敗訊號 + 護欄理由） | 只有文字目標 / 缺失敗訊號 / 缺護欄理由 | 空白 |
| 使用者 | 角色 + 情境 + workaround | 缺任一項 | 空白或「一般用戶」 |
| 功能需求 | P0 ≥1 則且有 AC | 有 Story 缺 AC | 空白或只有功能列表 |
| 技術考量 | 有內容或明確 [待工程確認] | 模糊描述 | 空白 |
| UI/UX | 有流程描述或設計稿連結 | 只寫「待設計」 | 空白 |
| 開放問題 | 有清單或明確「無開放問題」 | — | 空白 |
| Unknown Register | 正文未知標記全入冊 | 部分未入冊 | 整節缺失 |
| Delivery Feasibility | 六欄全填（含 [待確認]） | 缺欄位 | 整節空白 |

**Metrics 評分依 Maturity 層級**：L1 草稿不得用 L2/L3 標準評。詳見 `build-report.md`。

---

## Gotchas

- **快照之後必須停**：不能在快照後面繼續問問題或輸出內容，等 PM 的 A/B/C 才能繼續
- **建議理由只能一條，且要有依據**：不是每個 [缺口] 都需要建議，只有有理由的才寫
- **C 是合法選項**：PM 選 C 代表有意識地決定跳過，後續不應該重複提醒這個缺口
- **B 和 C 的差別**：B 是「知道有缺口，明確要追蹤」；C 是「知道有缺口，不想追蹤」。兩者都要尊重，不能把 B 的追蹤強加給選 C 的 PM
- **Story 和 Metrics 也用同樣的快照邏輯**：Guided Mode 下每則 Story 或每個 Metric 定義完後，同樣給快照等回應，不自動繼續下一則
- **Draft Mode 不出快照**：使用者沒明示要 Guided Mode 時，預設為 Draft Mode，全文一次輸出後統一附 Unknown Register 與校準清單，不逐章停
- **PM 不回應不等於通過**：若 PM 未回應快照，不得視為正式確認。下次延續時，沿用本次草稿作為工作版本，但所有 `[待確認]` 仍維持未確認狀態
