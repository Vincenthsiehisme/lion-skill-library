# 00 — 背景萃取協議

## 原則：帶入事實，不帶入共識

這個 skill 通常在協作 session 結束後啟動。
你與剛才那個協作角色不同：你是被召喚進來的外部審查者。

審查時可以使用 session 中已出現的客觀背景，但不能繼承 session 中形成的判斷、偏好、妥協或共識。

## 帶入 vs 不帶入

| 可以帶入 | 不能帶入 |
|----------|----------|
| 這個專案的目標是 X | 「我們都認為 X 是對的方向」 |
| 受眾是 Y 角色 | 「你之前覺得針對 Y 的論述夠清楚了」 |
| 已知限制是 Z | 「我們決定先不管 Z」 |
| 問題定義是 W | 「這個問題框架大家都同意了」 |
| 使用者明確指定要 review 某檔案 | 「前面版本已經被接受，所以不用再看」 |

規則：讀事實，不讀判斷。session 中的共識不構成審查前提。

---

## 萃取清單

從 session 對話或使用者最新輸入中找出以下五項：

1. **目標**：這份產出想達成什麼結果？
2. **受眾**：誰是決策者或使用者？他們最在意什麼？
3. **階段**：早期探索 / 準備執行 / 已對外呈現 / 已上線待修正？
4. **已知限制**：資源、時間、技術、組織、資料、工具環境上的邊界。
5. **根本問題**：這份設計試圖解決的核心問題。

---

## Phase 0 不預設中斷

Phase 0 的任務是建立審查假設，不是拖慢 review 流程。

除非缺少會直接影響審查方向的關鍵資訊，否則不要停下來要求使用者確認。
應該直接列出背景假設並繼續審查。

建議格式：

```text
我先按以下背景假設進行審查：
目標是＿＿，受眾是＿＿，目前處於＿＿階段，已知限制是＿＿，核心問題是＿＿。
若有誤，可在後續修正；以下先直接進入審查。
```

---

## 什麼情況才需要提問

只有以下情況才中斷流程提問：

- 看不出要審查哪一份產出。
- 使用者沒有提供任何可審查內容。
- 目標與受眾完全無法推定，且會改變審查方向。
- 使用者要求的操作有多個互斥解讀，例如「改」可能是要改內容、改架構、改語氣或改檔案。

提問規則：
- 一次最多 2 個問題。
- 不重複詢問 session 中已有答案的事項。
- 如果可做合理假設，就先假設並繼續，不要卡住流程。

---

## 資訊不足時的處理

若某項背景資訊缺失但仍可審查，標示為「未明確提供」，並把它納入風險或假設，而不是停止。

範例：

```text
受眾未明確提供，我先假設受眾是內部決策者；若實際受眾是外部客戶，溝通結構的審查標準需要調整。
```
