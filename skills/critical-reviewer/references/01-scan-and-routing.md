# 01 — 掃描與顧問召集

## Phase 1A：被審查物類型分流

快速掃描前，先判斷這份產出屬於哪一類。不同類型的文件不能用同一組審查標準。

| 類型 | 主要審查重點 | 常見盲點 |
|------|--------------|----------|
| Skill / Prompt | 觸發條件、上下文邊界、輸出格式、fallback、工具依賴、幻覺風險 | 把理想行為寫成保證、沒有 fallback、角色過度擬人化 |
| PRD | 目標、使用者、範圍、AC、依賴、上線風險、驗收邏輯 | 功能清楚但問題不清楚、AC 不可測、依賴未列 |
| 系統設計 | 邊界、資料流、source of truth、版本、狀態、例外流程、失敗路徑 | 邊界模糊、共用資料未定主、異常狀態缺席 |
| 策略報告 | 核心主張、證據鏈、受眾決策問題、取捨、機會成本 | 論點漂亮但不可決策、證據只支持不挑戰 |
| 流程設計 | 角色責任、交接點、狀態轉換、異常處理、稽核紀錄 | 流程圖完整但責任不清、例外情境未設計 |
| 分析報告 | 指標定義、資料來源、推論鏈、混淆因子、行動建議 | 數字正確但推論跳躍、沒有指出限制 |

若類型混合，選主要交付目的作為主類型，並在掃描摘要中標示次要類型。

---

## Phase 1B：快速掃描（60 秒診斷）

快速閱讀產出，不做深度分析，只判斷以下維度的初始狀態：

```text
□ 文件類型：這份產出是 Skill、PRD、系統設計、策略報告、流程設計、分析報告，還是混合型？
□ 問題結構：有沒有明顯的 MECE 缺口？方案選項有重疊或遺漏嗎？
□ 用戶假設：洞察是事實還是推測？有沒有驗證依據？
□ 執行依賴：前提條件是否被明確列出？依賴是否過多？
□ 結論結構：結論先行還是埋在最後？論點順序清晰嗎？
□ 類型特有風險：此文件類型最容易出錯的點是否被處理？
```

輸出掃描摘要（2–3 句）＋召集決定：

```text
快速掃描後，這份產出屬於＿＿類型，主要問題集中在＿＿。
我將召集：[顧問名單] 進行深度審查；另有＿＿問題可在整合段直接處理，不需召集額外顧問。
```

## Phase 2：顧問召集邏輯

| 掃描發現 | 召集顧問 |
|---------|---------|
| 問題分解有重疊／遺漏、方向模糊、機會成本未評估 | [策略顧問] |
| 用戶洞察多為推測、結論缺乏根據、需求未被驗證 | [使用者研究員] |
| 執行假設樂觀、風險維度缺失、依賴條件脆弱、fallback 不足 | [風險顧問] |
| 結論埋在最後、論點順序混亂 | 不召集額外顧問，整合段直接套用 Pyramid Principle 重組 |
| Skill / Prompt 的工具依賴、上下文邊界或 fallback 有問題 | 優先召集 [風險顧問]，必要時加 [策略顧問] |
| 系統設計的 source of truth、版本、狀態或資料流模糊 | 優先召集 [策略顧問] 與 [風險顧問] |
| PRD 的使用者、情境或 AC 不清 | 優先召集 [使用者研究員]，必要時加 [風險顧問] |

## 召集原則

- 通常召集 2 位顧問，保持聚焦。
- 問題分散才召集全員。
- 沒有關鍵發現的顧問不展開發言；沉默比虛假批判更有價值。
- 掃描發現同時符合多個條件時，優先召集問題最嚴重的那位。
- 若只召集 1 位顧問，也必須在整合段說明沒有獨立收斂，避免硬湊。

## 顧問召集紀錄

每次輸出都應保留召集紀錄，讓使用者知道誰被召集、誰沒被召集、誰被召集但不展開。

格式：

```text
顧問召集紀錄：
- [策略顧問]：召集，原因是＿＿；展開＿＿個問題。
- [使用者研究員]：未召集，原因是＿＿。
- [風險顧問]：召集但不展開，原因是掃描後未發現足夠高優先級的失敗路徑。
```

狀態定義：

| 狀態 | 說明 |
|------|------|
| 召集並展開 | 該顧問有高優先級發現，進入 Phase 3 詳述。 |
| 召集但不展開 | 掃描時有疑點，但深挖後不足以形成問題。要記錄原因，不硬湊。 |
| 未召集 | 該視角不是本次主要缺口。要簡述原因。 |

## 嚴格度校準

依使用者確認或推定的階段自動調整：

| 階段 | 嚴格度 | 框架要求 |
|------|--------|---------|
| 早期探索 | 中 | MECE + 假設驅動為主，其餘選用 |
| 準備執行 | 高 | 被召集顧問必須完整套用各自框架 |
| 已對外呈現 | 極高 | 加入溝通結構的全面審查 |
| 已上線待修正 | 極高 | 加入失敗路徑、事故回溯與可觀測性審查 |
